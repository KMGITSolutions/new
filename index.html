01LanguageLesson

Domain Language#

Ever since AI coding became viable, the thing so many people underestimate is communication. The quality of that communication between user and agent is going to be a big factor in determining the quality of the output.

The language we use, the things we define, how compressed or verbose that language is - all of it has a huge impact.

Models these days have a reputation for being pretty hard to talk to. Consider asking an agent about Cadence, our course platform: "Can a learner get their money back?"

It might reply with:

The reversal eligibility envelope is evaluated by the cancellation gate, which defers to the chargeback settlement handler once the entitlement lease is released.

That answer contains four invented names, terms that simply don't exist in the codebase. The agent decided to start calling things by these names itself.

The reason agents invent names like this is efficiency. Squeezing lots of meaning into a small name means it can reuse that name again and again without having to explain itself every time. But for a user who doesn't know what these terms mean, it's a nightmare.

A Shared Vocabulary Fixes This#

The best way around this is a shared vocabulary: a GLOSSARY.md file used for communicating between the user and the agent.

It sounds incredibly simple, but this technique has ramifications further down the line. It's one of the best techniques for:

  • Increasing the quality of your communication with the agent
  • Increasing the agent's quality of output
  • Improving your codebase
  • Improving the experience for your users downstream

The Cost of Inconsistent Language#

This isn't just a theoretical problem. There's a live issue in our demo application, Cadence, that isn't really a bug, it's a language issue.

If we log in as Liam Thompson and go to his Introduction to TypeScript course, the course page offers a button labelled "Cancel my purchase".

After submitting, the terminal prints the confirmation email sent to Liam. That email uses a completely different word:

Text
subject: Reversal requested — Introduction to TypeScript

Hi Liam Thompson,

We have your Reversal request for "Introduction to TypeScript".
The Reversal is for $79.00, the amount you paid.

Our team reviews every Reversal by hand. You do not need to do
anything else — we will email you again when it is done.

— The Cadence team

And then on the account settings page, a third name appears:

"Pending Chargeback."

So Liam asked to cancel his purchase, got an email saying his Reversal request was accepted, and now sees a Pending Chargeback on his account. Three names for the same thing. That kind of inconsistent language is a nightmare for users.

The Drift Lives in the Code Too#

It's not just the UI - the same drift exists in the code identifiers:

NameWhere it lives
getCancellationOfferapp/routes/courses.$slug.tsx
buildReversalEmailapp/routes/courses.$slug.refund.ts
pendingChargebacksapp/routes/settings.tsx

Any agent walking through this setup has to find all these different names for the same thing. And because it can't, code gets duplicated, because the agent simply can't find what it's looking for.

Fixing Language With /grill-with-docs#

The fix is: when you're figuring out what you want to build, also figure out the language you want to use to build it.

The way to do this is an improvement to the /grill-me skill called /grill-with-docs. It builds on two skills layered together:

  • grilling - the foundation, the same relentless interview as /grill-me
  • domain-modeling - layered on top, which actively challenges your language as you work through a grilling session

The domain-modeling skill:

  • Challenges terms
  • Invents edge-case scenarios
  • Writes a glossary and a set of decision records the moment they crystallise

The files it writes are GLOSSARY.md and entries in docs/adr/. Every other skill in the setup then reads from this glossary to ensure it's using consistent language.

Throughout this section, we're going to learn how to replace /grill-me with /grill-with-docs, settle these language decisions, and turn them into a clean codebase, and a better product too.

Ubiquitous Language#

A lot of the ideas here come from Domain-Driven Design by Eric Evans. DDD calls this a Ubiquitous Language.

This is a big, thick book, and we're really taking just one or two ideas from it. None of the hardcore stuff - no aggregates, no event sourcing. Just a glossary and the application of that glossary.

The one big thing to take from that book is the word ubiquitous. This language has to be the same everywhere it's used:

  • The way the team talks about the product
  • The product UI itself
  • The code

The moment you figure out the right name for the thing you're building, you've basically built the thing, because you understand how to use it in conversation, how to talk about it, and how to frame it to the agent so it can build it.

In our exploration of grill-with-docs, we've been looking at the domain-modeling skill, glossaries, scenario testing, figuring things out. But we've not really looked at the other thing the domain-modeling skill does: editing and creating ADRs.

What Are ADRs?#

ADRs are Architectural Decision Records. They are records of decisions taken.

The reason they exist is quite simple. If you read code, especially comments, or the implementation itself, that code can tell you what it does. If the code is well structured, it can tell you exactly what it returns, it can use your domain language, it can explain everything about itself.

In other words, code can tell you what you ended up with. But it can't tell you all the things you decided against, the approaches you didn't take.

Code is like the answer with all of the working rubbed out.

That working is what ADRs are for. They're a list of all the major decisions made inside a repository or project, there to preserve history so we don't make the same mistakes again.

The ADR Format#

The format is defined in .agents/skills/domain-modeling/ADR-FORMAT.md. The basic template is intentionally tiny:

Markdown
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}

That's it. An ADR can be a single paragraph. You can have optional sections:

  • Considered Options - only when the rejected alternatives are worth remembering
  • Consequences - only when non-obvious downstream effects need to be called out

But the ADR needs to be very small and very tight.

Offer ADRs Sparingly#

As soon as people see this, they think: if you give an agent a folder full of markdown files, it is just going to keep adding to them. The folder is just going to grow and grow.

So what is the criteria for adding an ADR? The bottom of .agents/skills/domain-modeling/SKILL.md covers this:

Markdown
### Offer ADRs sparingly

Only offer to create an ADR when all three are true:

1. **Hard to reverse**: the cost of changing your mind later is meaningful
2. **Surprising without context**: a future reader will wonder "why did they do it this way?"
3. **The result of a real trade-off**: there were genuine alternatives and you picked one for specific reasons

If any of the three is missing, skip the ADR.

Here's how those criteria play out in practice:

DecisionHard to reverse?Surprising?Real trade-off?Needs ADR?
Use Recharts for chartsNoNoNoNo
Use Sonner for toastsNoNoNoNo
Move from React to VueYesYesYesYes

Picking a library like Recharts or Sonner is easy to strip out and replace. But moving from React to Vue is a decision that would take a lot of hours to walk back, and that's the kind of thing worth recording.

A Worked Example: The Refund Window#

Let's make this concrete. In app/routes/courses.$slug.tsx, there's an asDayString helper, called inside getRefundOffer just below it.

The function returns what the learner is offered if they want their money back, or null if the purchase can't be refunded.

The key decision is in how isWithinWindow is calculated:

TypeScript
// Compare whole days, not hours - a purchase at 23:00 should still get its
// full fourteenth day.
function asDayString(when: Date) {
  const year = when.getFullYear();
  const month = String(when.getMonth() + 1).padStart(2, "0");
  const day = String(when.getDate()).padStart(2, "0");
  return `${year}-${month}-${day}`;
}

function getRefundOffer(userId: number, course: { id: number }) {
  const purchase = getPurchaseForCourse(userId, course.id);

  if (!purchase) return null;
  if (getOpenRefundRequest(purchase.id)) return null;

  const purchasedDay = asDayString(new Date(purchase.createdAt));
  const windowEnd = new Date(purchase.createdAt);
  windowEnd.setDate(windowEnd.getDate() + REFUND_WINDOW_DAYS);
  const lastDayInWindow = asDayString(windowEnd);
  const todayDay = asDayString(new Date());
  const isWithinWindow =
    todayDay >= purchasedDay && todayDay <= lastDayInWindow;

  if (!isWithinWindow) return null;

The refund window is counted in whole days, not hours. Here's why that matters:

  • If a user purchases on the 20th of September at 9am...
  • Counting in hours: the window shuts at 9am on 4th October
  • Counting in whole days: the window shuts at midnight at the end of 4th October

The whole-days approach gives the learner a more generous refund window. But this is pretty surprising without context. An agent could totally ignore this while working through the code, and just switch freely between hours and whole days.

The only place this decision is currently recorded is the comment directly above asDayString. It's just noted down in the code, and not obvious elsewhere.

Why ADRs Live at the Top Level#

Having decisions in a global docs/adr/ folder at the top of the repo means the agent can find them and surface them more easily.

It's also important to capture them at the right moment. When you're grilling, that's the moment you're making decisions, so it makes sense to turn the important ones into Architectural Decision Records right then. That's why grill-with-docs does domain modeling and ADRs at the same time.

ADRs vs. Secondary Sources#

It's worth addressing a common concern. Adding markdown files to a repository that describe what the code does is risky.

The codebase is a primary source. It's large, but it's the source of truth, the stuff that actually executes. A specification or docs file is a secondary source: much smaller, but not actually true by definition. Secondary sources can go out of date and confuse the agent.

The thing about an ADR is that it's meant to fill in only the gaps you can't see from the code:

  • It is not a new source of truth for what the code is supposed to do
  • It is only there to explain the stuff the code can't explain itself

The same is true for the glossary. Understanding the glossary allows you to navigate the code more easily. Both document types exist purely to fill in what the code can't answer for itself, and both are worth the time and tokens it takes to create and maintain them.

Q&A#

With that, we've got a good handle on how domain language works, how ADRs work, and how to use Grill with Docs to sharpen your language before you get started.

Let's go through a few commonly asked questions about this approach.

Is one glossary always enough?#

What happens when your app gets bigger and bigger? There's already a good example in the application that we haven't glossaried yet: questions and answers in Cadence.

Quizzes have questions. As part of a quiz, the learner gets asked a question, which they provide answers to. All of these have entities in the database.

But lessons also have discussions, where learners can ask questions and instructors have a view of all the answers in the discussion.

If we use the word "question" for both of these, that gets confusing pretty quickly.

Prefix the entity#

One simple way to handle this is to always prefix the entity. You always know whether you're talking about the quiz question or the discussion question, and you never refer to something as just a "question".

TermWhere it lives
Quiz questionAsked to a learner as part of a quiz
Discussion questionAsked by a learner in a lesson discussion

This is similar to what we already have with platform admins and team admins. They are never referred to on their own as "admin", and that's specifically mentioned in the avoid section.

When prefixing isn't enough#

You might get to a point where you're doing way too much prefixing. You realize there are actually two different conversations happening, each using different words.

Eric Evans talks about this in Domain-Driven Design, where he says multiple models are in play on any large project.

In an ideal world, a large company uses a single set of language to talk about its business. In practice, this is often different in different parts of the organization.

Take the refund and chargeback language we looked at earlier:

TeamHow they use the language
Product"Refund" describes a request and its outcome
FinanceA much deeper model, with a difference between a refund and a chargeback

The product simply doesn't need to care about the difference that finance has.

Both teams are right. This is just two ubiquitous languages being used in the same company. In DDD, you call each one a bounded context: the context within which that part of the company operates.

Both parts of the company might have developers who contribute to the same repository. If you have different bounded contexts inside your repository, you want to make that really explicit.

Splitting with the domain modeling skill#

I've thought of this in the domain modeling skill. A repo can have either:

  • A single context, with a single bounded context at the root.
  • A GLOSSARY-MAP.md, which maps to different glossaries in different parts of the application.

So even with different bounded contexts, different ways of speaking within the same repository, the domain modeling skill can handle it.

You can also have different ADRs within a bounded context. There's a global set of ADRs that you can append to if they affect the entire company, or you can write ADRs just for one bounded context.

The rule: split whenever you feel like two bounded contexts are trying to fit into the same glossary.

Say you have the loop where you grill with docs, go to spec, then tickets, implement, and code review. At what point do you merge the changes to the glossary?

In my opinion, as soon as you've made the decision, and maybe agreed with your team that this is the term you want to use. Do it even before you've written the spec.

By the time you reach the implement step, the code base is already in line with how you want it to look. You can also update glossary.md yourself and make sure it looks exactly how you want before moving on to spec and tickets.

That way, when the spec and tickets are created, they point to files that have already been renamed, and the code base is easier to navigate.

How do you pick good words?#

What do good glossary terms actually look like? Most of the time, we're building applications for other people. Real people who are going to use this stuff in the world to do things.

The best domain language comes from your users.

If you can match the language used in the product with the way people think about using it, you end up with a product that's easy to use and easy to work on.

So the answer is simple. Really listen to your users, and mine the words they use for ideas for the glossary and for how to build the application.

This is especially true early in a project. You want conversations with lots of users to think about how to model the thing they need built.

Do you need the glossary first?#

Does Grill with Docs need a glossary, or can you build one up as you go?

I hope these lessons have shown you that you can work with no glossary whatsoever and build it up slowly, clarifying the picture as you grow.

In my opinion, the glossary is never quite finished. There's always something that could be defined and is on the edge of being defined.

Adding to the glossary and pruning it is pretty hard work. There's a lot of thinking to do, because you're clarifying the product in real time.

So go slowly, and only create the entries you need for building the thing you're building. Rushing is also how you end up with poor quality entries that you then need to prune.

Can an agent own the glossary?#

Another question I get a lot: can an agent own the glossary and be responsible for it, without a human in the loop at all?

In my opinion, this is the fastest way to turn your glossary into an absolute dumpster fire.

The point of this language is that it's ubiquitous. It's used in the code, by the team, and in the product. Crucially, the team is humans and it's now also agents.

If the agent goes off and invents its own terminology, that won't sit well with the team, because the team will be using different language from the agent.

So no, an agent cannot own the glossary on its own. Working on the glossary is one of the highest value ways a human can contribute to the health of the code base.

Agents can write markdown fine, the risk is more entries of poor quality rather than too few, and bounded contexts are not a limit on agents.

The Limits Of One Session#

Later in this course, we are going to look at how you can automate the creation of work. When you have an idea that you need to build, you can pass it off to an agent and it will go away and build it.

This is very exciting. When I first noticed it, I realized something interesting: the bottleneck has moved.

Instead of the bottleneck being that the work needs to be done, the bottleneck is now that the work needs to be planned.

So I started thinking about how to make a planning setup that lets me plan huge chunks of work. They needed to be big enough that I could actually saturate the number of agents I have available to work on it.

Problems with single-session grilling#

The annoying thing I noticed was that grilling wasn't quite cutting it for me. The reason was pretty simple: grilling is one session.

As you answer more questions, add more questions and talk more with the agent, you eventually reach a point where you're going into the dumb zone.

What happens at 200,000 tokens?#

This is a question I get a lot. When you're doing a grill-with-docs session, what do you do when it reaches 200,000 or 300,000 tokens?

The annoying thing is that this session history is really valuable. It has all of your answers and all of your thinking in it. If you compact it to make it smaller, you often lose really rich information.

Splitting across sessions#

Some people split the work into multiple sessions. They say, "I've got this idea that I need to figure out. I'm going to grill part of it in one session and another part in another session."

But that can be really tricky. What if questions in session one relate to questions in session two? It just gets really painful.

Prototyping makes it worse#

This is especially true when you start prototyping. Say you're in a grill-with-docs session and you realize you want to build some kind of prototype.

So you open another session just to figure out that thing, and then maybe hand it back to the grill-with-docs session.

You end up doing an awful lot of context management and session switching, and it felt pretty painful to me.

The worst part is that you need to know the shape of what you're doing up front, so you can work out how many sessions to break it into. All of that just felt really strange.

Lessons from Shape Up#

Whenever my process of working with agents feels wrong or off, it helps me to go back to what I was doing pre-AI and mine that for ideas.

My Bible for this, pre-AI, was Shape Up by Ryan Singer. It's a book all about finding the right shape of work, having discussions at the right fidelity, and then shipping the right thing.

Understanding planning fidelity#

It's worth defining what I mean by fidelity. Whenever you're planning work, you can do that planning at a low fidelity or at a high fidelity.

Here is the ladder, from lowest to highest:

FidelityWhat it looks like
DiscussionGrilling, and figuring out the language you want to use to describe the feature
BreadboardingFiguring out the actions needed, using boxes and arrows
WireframesSeeing how it's organized on the page, linking things to different pages and understanding how it's shaped
PrototypingHalf-working code
Working codeActual code, working in production

Low fidelity means low commitment. You're just talking about something, and you haven't committed any tokens to building it yet.

Higher fidelity is more committing. It takes more tokens to get there, and you have a better idea of where you're going, but of course it's slower.

Agents enable higher fidelity#

The cool thing about agents is that they let you work at a higher fidelity than you were used to, because prototypes are now really cheap to produce.

It's still important to stay at low fidelity and discussion for some things. But I wanted a technique that would push me towards high fidelity when that was useful.

Those were the two problems I wanted to solve:

  • Nasty session management during planning
  • Working at the correct fidelity, all the time

Introducing Wayfinder#

This is how I came up with Wayfinder. It's a planning skill that lets you plan work of any size over multiple sessions, and it chooses the right fidelity for each part of the plan.

It really is amazing for planning work with lots of unknown unknowns. That means tons of things you need to validate, and things where you have no idea how they'll integrate into your application or how you'll build them.

Essentially, if you don't know how you're going to get there, you can use Wayfinder to find your way.

In this section, we are going to master using Wayfinder for planning really hard things and also really big things.

The opening of the skill#

The skill starts with a rather poetic opening: a loose idea has arrived, too big for one agent session and wrapped in fog.

A map has sub-tickets based on it. Each of these is technically a ticket in your issue tracker. In our case they are GitHub issues.

  • The map is a GitHub issue.
  • Each decision ticket is also a GitHub issue underneath it.

Resolving the map#

You go through and resolve the decision tickets one at a time. Once you've resolved all of them, essentially closing the issues, your map is ready to go.

In other words, you have made all the decisions needed. You have found your way to your destination.

The destination#

But what is your destination? That is what you decide in your very first session. The way from here to the destination isn't visible yet, and wayfinding is about finding that way.

The skill puts it like this: the destination varies per effort, and naming it is the first act of charting. It shapes every ticket.

The destination is the first thing you decide. Once you have it, you can figure out the way there.

One really cool thing about Wayfinder is that you can use it for non-coding work. I have a Wayfinder map for this course, and the destination is the finished course.

A spec as the destination#

For coding, I recommend making the destination a spec. That is how we're going to use it in this course.

We decide everything that might need to go into the specification and create a really detailed spec. Then we hand it off to some agents to build it for us.

So far we've used grill-with-docs as our pre-spec ritual for big chunks of work. But it's best for neatly scoped work.

Wayfinder is good for large projects, huge chunks of work. We create big specs out of them and run them through our normal loop.

The map in detail#

Let's look at these data structures more closely.

The map is a single issue on this repo's issue tracker, labeled wayfinder:map. Its decision tickets are child issues of the map.

The map acts as an index of all the decisions taken. When we turn the map into a spec with /to-spec, the spec has the map as its index, its entry point to all the decisions made.

Each ticket then holds all the detail: the grilling sessions and everything that led to the decisions.

In other words, the whole map is a low-resolution view. It contains:

  • The destination.
  • Some general notes.
  • All the decisions made so far.
  • All of the fog of war around those decisions.

Fog of war#

Fog of war is a metaphor I'm really proud of.

When you're planning big chunks of work, you often won't know your way to the destination. If you knew everything you needed to do and decide, work would be a lot easier.

You can only see a few decisions in front of you at any one time. You can't see the whole board. As you go through the map, you reveal more of it.

Blocking and the frontier#

Crucial to this is that tickets can have blocking relationships to each other.

For instance, both of two decisions might need to be made before we can make a third. Only when those two tickets are closed can we open the third.

We can use the issue tracker's native dependency tracking for this. GitHub, for instance, has a "blocked by" feature that lets tickets be blocked by others.

A ticket is unblocked when every ticket blocking it is closed. The frontier is the open, unblocked, unclaimed children.

In this map, number four is blocked because numbers two and three haven't been closed yet. Two and three are the frontier of open tickets, so they can be tackled at the same time.

Clearing the fog#

How do you clear the fog of war and make your way to the destination?

As you make decisions, they reveal more decisions you need to make. During the wayfinding session for number two, another ticket might present itself.

So you create ticket number five and add it to the map.

Once number five is done, you may realize you can see your way to the destination. We have everything we need. Once you've completed number six, the destination is complete and the map can be turned into a spec.

These tickets form a graph, a directed acyclic graph if you want to be technical. Decisions inside the tickets open up more space and clear the fog of war, so you can figure out your way to the destination.

Some maps can have 50 or 60 tickets. They can scale to enormous specifications and projects.

The four ticket types#

What are you actually doing inside these tickets? There are four types in Wayfinder, each used for different things.

TypeUsed forMode
GrillingAnswering a list of questions in a standard grilling sessionWith you
PrototypeRaising fidelity by making something to react toWith you
ResearchFetching third-party information you don't have locallyAFK, a sub-agent
TaskManual work that must happen before a decisionA checklist for you

Grilling#

The most common type is the grilling ticket. In one agent session, you answer a list of questions, in a standard grill-with-docs session.

In the skill's ticket types, grilling is the conversation, the default case. It says to always call the skill tool twice, for grilling and domain modeling.

Prototype#

Grilling is quite low fidelity. It's discussion. What if we need something higher fidelity? What if we need to look at something before we can decide which way to go?

For that we have prototype tickets. They let you raise the fidelity on questions where you need to see something working.

A prototype ticket raises the fidelity of the discussion by making a cheap, rough, concrete artifact to react to. It calls a separate skill, prototype.

The skill says to use it when "how should it look" or "how should it behave" is the key question.

Research#

A research ticket is for when you need third-party information or data you don't have access to locally.

That means reading documentation, third-party APIs, or local resources like knowledge bases, to surface a fact that a decision waits on.

Sometimes we can't grill anything until we have the information we need, and research goes out and gets it.

Unlike the others, this one doesn't need your help. It is AFK, away from keyboard, and is resolved immediately by a sub-agent.

The ticket is created and then immediately scheduled to a sub-agent. The sub-agent does the research and attaches it to the ticket.

This is very useful. Once you've done your grilling session, you can get to the prototype immediately.

Task#

Finally, the task ticket is for manual work that must happen before a decision can be made.

That might be signing up for a service so we can build a prototype, provisioning access to something, or moving data into a certain shape.

This one isn't really a decision ticket. The agent creates a list of manual steps for you to follow, such as provisioning the service, so that what needs doing gets done.

Invoking Wayfinder#

How do you get Wayfinder to create the map and run the tickets? There are two modes, and it detects which one you want.

  • Run /wayfinder with a prompt, and it creates a new map. It has a grilling session with you to decide where you're going and what your destination is.
  • Once the map exists, run /wayfinder with a ticket number in a new session. It runs a Wayfinder session to tackle that specific ticket.

Grill vs Wayfinder vs Ship First#

We've now seen what a full Wayfinder flow looks like. It runs from grilling, to prototyping, to research, to creating tasks, to turning that into a spec, to implementing that spec.

You'll probably agree this is a pretty heavy flow. When you walk through it yourself, you'll be faster than me, because you won't be explaining it as you go.

But it's still a lot of grilling sessions, a lot of prototyping and a lot of thinking before the agent does anything.

Three options#

So the question becomes: when should you use Grill with Docs, and when should you use Wayfinder?

There's also a third option that I haven't really talked about before: when do you not use Grill with Docs at all? When do you one-shot the code?

OptionWhat it does
One-shotGet the agent to create the code without grilling first.
/grill-with-docsGet the agent to ask you questions before you begin work.
/wayfinderAlign over multiple sessions, creating prototypes and completing tasks as you go.

The decision tree#

Of course, I have a decision tree for you.

At the top, you have a new session. You want to create a new piece of work, and you don't know which approach to choose.

Is the diff tiny?#

My first question is: is the diff the thing you're going to create tiny?

In other words:

  • Are you changing the color of a button?
  • Are you making a failing test pass?
  • Is the thing you're reviewing really, really small?

If it's that small, you don't need to worry about misalignment with the agent.

Why grilling exists#

Grill Me and Grill with Docs help prevent a specific pain. You create a huge diff, and it isn't at all what you wanted. You've wasted a ton of tokens and a ton of time creating something worthless to you.

But if the diff is really small, it barely matters if it's worthless. It's small enough that the agent can recreate it really quickly.

One-shotting small changes#

So often I'll say, "just go and do your work and see how you get on," and I'll review it afterwards.

I do this constantly for little things in QA:

  • Change this icon.
  • Change this text.
  • This is maybe too big.
  • The margins are too large.

That's loads of stuff, especially for UI. For those cases, I recommend one-shotting. Honestly, I've been using it more and more.

Start with Grill with Docs#

For anything where the diff is even medium sized, anything that isn't tiny, Grill with Docs works really well.

I actually recommend you start every session that you're not planning to one-shot with Grill with Docs.

Graduating to Wayfinder#

Why? Because you can always graduate from Grill with Docs to a Wayfinder session.

Say you're in a Grill with Docs session and you realize you're going into the dumb zone, and this is going to be way bigger than you thought. From inside the session, you can say:

Text
Let's turn this into a wayfinding map.

That makes your initial decision really easy. You're just deciding between Grill with Docs and one-shot.

The failure case of starting with Wayfinder#

The failure case is starting with Wayfinder, then realizing you've done all of this ceremony and created a big map, when the work is way simpler than you thought.

That's much harder to recover from, because you've already created all these assets.

So I always recommend starting with Grill with Docs. If you feel there's way more fog than you expected, and this feels huge, you graduate to Wayfinder.

The decision tree, summarized#

This is your decision tree:

  1. Is the diff tiny? Can you review it quickly, and does it cost almost no time to try again? If so, one-shot it and align after you see the diff.
  2. Otherwise, start with /grill-with-docs. Align before you build, and firm up your domain language.
  3. If the grilling session is going into the dumb zone, or there's more fog than expected, turn your initial grilling session into a Wayfinder map and go from there.

You don't have to grill with docs everything. You certainly don't have to wayfind everything. You can be one-shotting more stuff than you think.

And you can use Wayfinder as an escape hatch for when Grill with Docs gets too crazy.

The Three Kinds Of Review#

We now know how to align with our agent, and we know how to plan huge chunks of work. We are starting to move towards setting up our software factory.

However, a software factory is a bit like driving a car. When you are learning to drive, what is the first thing you need to learn? You need to learn how to slow the car down.

If you only focus on the ways you can accelerate and push forward your software factory, you will end up with a massive slop cannon.

We need to find ways to slow down and increase the quality of what we ship, so that we don't burn out.

The three brakes#

I think of there being three main brakes in our software factory. Brakes are the things that slow the car down.

BrakeWhat it isDriven by
Automated checksDeterministic checks on the quality of the codeCPU cycles
Automated reviewReview of the codeAgents
Human reviewAn actual human checking the codeYou

Automated checks#

First, we have automated checks. These are deterministic checks that check on the quality of the code:

  • Unit tests
  • Type checking
  • Linters
  • Various other types of check that we can layer over our application

These are incredibly useful because they only cost CPU cycles. They don't cost tokens.

So you can really go nuts with this, layering up tons of automated checks to make sure your agent does what you want it to.

Automated review#

Then we have automated review on top of that. This is different because it is driven by agents.

We have already seen a little of this with the /code-review skill. We have used it in the cohort, and we saw it in action in the previous section inside the implement spec skill.

There is a lot more juice to be squeezed out of automated review, so we are going to focus on that soon.

Human review#

The last layer, of course, is human review: an actual human checking the code.

What this section covers#

In this section, we are going to focus on the bottom two: automated review and human review. Automated checks will be covered later, in the feedback loop section.

We are going to look at:

  • The various ways you can improve human review
  • How much you should actually look at the code
  • In what circumstances you should look at the code

We are then going to use human review to improve our automated review. In theory, the automated review can start doing more, and the human review can start doing less.

Hopefully, by the end, once we have learned all three, we will be able to put the brakes on our software factory. That keeps quality high, even as we start shipping.

Goals for improving human review#

We are going to start our journey by looking at human review.

Specifically, we want to improve it in two ways:

  • Speed: make sure a PR can be understood by someone reviewing it as fast as possible.
  • Priority: make sure review time is prioritized correctly.

Not all PRs deserve the same treatment. Some PRs can be reviewed less than others.

Agents write bad PR descriptions#

Something I've noticed working with agents, and that I've sort of prayed would get better but never has, is that agents are still terrible at writing PR descriptions.

They write PR bodies that are full of garbage and really hard to review. That turns you off actually wanting to review the PR.

For a long time I had no idea how to fix this. I just thought agents were always going to write slop and that you couldn't control it.

The show-me skill#

That was until I found a gorgeous skill called show-me, by Dex Horthy at HumanLayer, who is a big inspiration for a lot of my work.

The show-me skill helps the user understand the current topic of conversation visually. It tells the agent to skip the preamble, keep prose brief, and use visual pseudocode explainers.

I have found these little explainers outrageously useful for:

  • Looking at UI
  • Looking at file responsibility
  • Component interaction
  • Understanding how things happen over time, with Mermaid diagrams
  • Diffs for component changes, file layout changes, and call tree or call stack changes

I started testing this out and I understood the intent of the change so much faster. Even before I was looking at the code, I understood why the code was being changed. That increased the speed of review.

Before and after evidence#

Speed has another component. You want to understand why the change is being made, but you also want to be sure the right change has been made.

So you want the agent to show you as much hard evidence as possible. That way you don't have to clone the branch, pull it down locally, poke around and test it yourself.

The next section in the PR body is the evidence, with a before showing a failure and an after showing a success.

We need the before so the agent can prove that what was happening before was actually broken. This is essential for bug fixes and new features. It gives the agent an extra hurdle to cross, and it proves to you that the thing is working.

The skill also describes what good evidence looks like:

Markdown
### Evidence

Concrete evidence that the change works. Show a before and after.

Screenshots are S-tier - when the environment is set up for it and the change is visual.

Execution-based evidence is A-tier. Test results, console output. Show the exact test that now fails and passes, using pseudocode.

In other words, the agent has to run the code to get console output and test results, and show the exact test that now fails and passes.

This evidence helps you review more speedily because you can have more confidence in the code. You can know at a basic level that the change is doing what it's supposed to.

Prioritizing which PRs to review#

What about the priority section? How do we prioritize the right PRs to review?

Even talking about review priority might feel controversial: the idea that we need to review some PRs and maybe not every PR. Before we talk about that properly, I want to frame it using the skill's framing.

Inside the PR body there is a Merge Danger section, made of a door and a blast radius.

One-way vs two-way doors#

The door idea is not original to me. I think it comes from AWS. It says every PR is either a one-way door or a two-way door.

  • Two-way door: you can walk through and walk back if you need to. You can merge the PR and then unmerge it.
  • One-way door: only goes one way. Walking through it makes something happen as a result, such as data loss, incurred cost, or a security implication.

A one-way door could be a change that sends an email to 50,000 people, or a breaking change in a public library.

One-way doors need to be reviewed much more closely than two-way doors.

Blast radius of a change#

The other thing in the Merge Danger section is the blast radius of the change. If something goes wrong, what are the potential ramifications?

This is different from the door. You can have a two-way door that is bad if it goes wrong, but you can easily walk it back. A one-way door with a massive blast radius, though? You had better believe I'm going to review that PR very closely.

DoorBlast radiusReview attention
Two-waySmallLowest. Might not need human review
Two-wayLargeBad if it goes wrong, but easy to walk back
One-wayLargeReview very closely

Both concepts together give you the priority to put on a PR.

Priority varies by project#

This differs not only by what the change is, but also by what the project is.

  • Personal software: probably 95% of your changes are two-way doors. With few users, you can change loads of stuff.
  • Medical or finance projects with big security implications: a lot of your changes will be one-way doors.

But not all of them will be. You can still prioritize certain PRs over others by looking closely at the door and the blast radius of the change.

You might even say that two-way doors with a small blast radius don't need human review. You can just review them on main.

Of course, if we want to skip human review, our automated checks and automated review need to be really solid first.

The /code-review Skill#

So far we've looked at human review. Now let's look at automated review.

In my opinion, most teams are not doing enough automated review. It is an amazing, very token-efficient way to save humans time.

The theory is that work moves through three stages:

  1. Automated checks
  2. Automated review
  3. Human review

The quality increases at each stage. By the time work reaches human review, you want the code to be as good as it can possibly be.

In other words, you don't want to waste human effort reviewing crap code.

Why not get the implementer to do it right first time?#

You may be wondering why we bother with automated review at all. Can't we just get the implementer to do its work right first time?

I've talked about this a bit in the crash course, but it's worth revisiting.

/implement has a lot of jobs to do. The agent doing the actual work needs to:

  1. Explore the codebase
  2. Implement
  3. Debug

A code review is a different shape of job. If you clear the context and review the diff that's been produced, the review agent:

  • doesn't need to find the diff
  • doesn't need to explore, because it's already in the right part of the codebase
  • doesn't have any files it really needs to change

That means you can load up the code review with a lot of instructions. Tweak this, do this, find these patterns and remove them or report on them.

Review runs in a sub-agent#

Usually you run a session with /implement, and then call /code-review from within it. The code review runs in a sub-agent.

In other words, it gets a fresh context window right then and there.

Loading up the review agent#

How do you load up this review agent? Look inside the code-review skill. At step 3, it identifies the standards sources:

`markdown

The Third Lens On Human Review#

So far, we've been looking at human review through two main lenses: increasing its speed, and working out how to prioritize it.

But I've been burying the lede, because there's a third thing that makes all of this make sense.

Whenever we're doing human review, we're not only reviewing the code to make sure it's doing the thing we want. We should also be thinking about improving the system that created the code.

Reviewing The Process, Not Just The Diff#

Any time we're piling through a diff, we should be looking for patterns we can warn the agent against next time.

  • "I like this."
  • "I don't like this."
  • "Maybe it should have done that."
  • "Maybe it shouldn't have done that."

The theory behind human review is that you should never have to leave the same comment twice.

Instead of constantly catching the agent's mistakes and reviewing the same garbage again and again, every comment you leave should go into the system and help improve it.

That means human review is there not only to improve the code, but also to improve two other things:
